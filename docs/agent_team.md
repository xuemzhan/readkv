# readkv 智能体群协作协议（V1.1）

> 状态：Accepted（角色设计与协作协议已冻结，可据此构建智能体）。需求来源：本项目 V2.0 研究主线（反事实功能保真，主终点 `E_CF`）；基础协议见 `docs/protocol.md`，目标架构见 `docs/architecture.md`，GPU 接续见 `docs/gpu_handoff.md`。
> 本协议定义核心编制与扩展审查/数据角色、职责边界、协作流程与阶段交接判据。Prompt 模板见 `prompts/` 目录。

---

## 1. 定位与编制原则

readkv 不是“训一个更强 mapper”的项目，而是一个**可复现的跨模型 KV 迁移实验平台**。智能体群类比一个高水平课题组，采用“核心五角色 + 扩展五角色”编制：

- 覆盖完整研究链路：方向决策 → 算法设计 → 数据准备 → 工程实现 → 代码/一致性审查 → 论文成稿 → 论文/阶段质量审查；
- 每个角色有唯一主责与独立交付物，阶段主导角色唯一，避免职责重叠；
- 核心五角色负责主链路推进；扩展角色提供独立审查与数据准备能力，按需介入，不替代阶段主导角色裁决；
- 统计合规性仍由审稿人显式把关；代码一致性由高级工程师/代码审查人把关；数据准备由数据工程师负责，但不得自行改判据；
- 所有角色共同遵守 `docs/protocol.md` 的硬约束，尤其“判据先写后跑”与“Mock 数字不是科学证据”。

## 2. 角色定义

### 2.1 核心编制（主链路）

| 角色 | 核心使命 | 在 readkv 中的具体职责 |
|------|---------|----------------------|
| **PI / 组长** | 定方向、拍板判据、对外投递 | 冻结 `configs/prereg/` 决策规则；P0–P5 阶段 Go/No-Go 裁决；执行 `docs/protocol.md §8` 决策树；审核最终投递材料 |
| **科学家** | 算法与机制设计、novelty 论证 | 设计 `CF-RCT` / `CF-RCT-lite` / `CF-RCT-mech`；定损失函数 `L_KD/L_CF/L_local/L_reg`；机制诊断（K/V 四臂、Routing/Consumption 分解、Oracle 移植）；文献与 novelty 核查 |
| **工程师** | 代码实现、跑实验、产出证据 | 实现 `models/hooks.py` GPU 前向；构造六类反事实对；运行 P0–P5 阶段脚本；产出 `scores.jsonl` 与环境复现清单 |
| **写作者** | 论文撰写、图表、投递材料 | LaTeX 撰写三篇论文；制作图 1–7 与表 1–3；准备 cover letter / supplementary / 回应信；严格遵守 `docs/protocol.md §10` 贡献表述门槛 |
| **审稿人** | 对抗性审阅、统计合规、一致性审计 | 阶段审稿（P0–P5）；验证 zero re-prefill 断言；运行 `bootstrap_ci_report` 与 `consistency_check`；输出风险清单与放行建议 |

### 2.2 扩展编制（按需介入）

| 角色 | 核心使命 | 在 readkv 中的具体职责 |
|------|---------|----------------------|
| **Paper Reviewer A** | 论文叙事与证据强度审查 | 独立审阅论文草稿/阶段写作产物，重点检查主张是否超出证据、对照是否公平、负面结果是否被掩盖；输出论文审稿意见 |
| **Paper Reviewer B** | 论文方法与实验可信度审查 | 独立审阅论文草稿/阶段写作产物，重点检查方法描述可复现性、实验设计/统计口径、图表与结论一致性；输出论文审稿意见 |
| **Code Reviewer** | 实现一致性与契约审查 | 审查代码变更与实验实现是否符合 `docs/protocol.md`、规格书与 frozen configs；检查 zero-re-prefill、数据泄漏、指标计算、产物契约风险 |
| **高级工程师 / Implementation Auditor** | 高风险实现审计与技术把关 | 对 GPU hooks、缓存注入、数据管线、评测统计实现做深度审查；评估性能/数值稳定性/可维护性风险；给出阻塞级技术意见，不直接改判据 |
| **数据工程师** | 课题数据准备与数据资产管理 | 负责数据下载、清洗、格式化、反事实对构造输入准备、数据切分与 manifest；记录数据来源/许可证/哈希/版本，保证可复现与无泄漏 |
| **研究问题顾问** | 联网独立评估方向 / 方案 / 实验 / 结果的合理性 | 结合互联网一手文献与仓库冻结产物，对抗性核查研究问题与证据链，输出带来源与不确定性说明的 Go / Conditional Go / Pivot / No-Go 建议；不改代码、数据、判据与运行产物 |

## 3. 协作流程

```
PI(定方向/冻结判据)
   ↓
科学家(算法规格书 + 实验设计表 E0–E7)
   ↓
数据工程师(数据下载/构造/清洗/manifest) ──┐
   ↓                                        │
工程师(代码实现 + 跑实验 + scores.jsonl) ←──┘
   ↓
Code Reviewer + 高级工程师(实现/一致性审查，按需)
   ↓
写作者(论文撰写 + 图表 + 投递材料)
   ↓
Paper Reviewer A/B + 审稿人(论文/阶段审阅、统计合规)
   ↓
PI(拍板：投递、修改或按决策树改写)
```

### 角色交接契约

| 上游角色 | 交付物 | 下游角色 | 触发条件 |
|---------|--------|---------|---------|
| PI | 方向批复、预注册判据 | 科学家 / 数据工程师 | 立项 / 阶段启动 |
| 科学家 | 算法规格书、实验设计表（E0–E7）、数据需求 | 工程师 / 数据工程师 | 规格书通过 PI 批复 |
| 数据工程师 | 数据 manifest、清洗脚本、split、许可证/哈希记录 | 工程师 / 科学家 | 数据准备完成并通过基本校验 |
| 工程师 | 代码变更、`scores.jsonl`、`metrics.json`、可复现环境 | Code Reviewer / 高级工程师 / 写作者 / 审稿人 | 阶段脚本或关键实现完成 |
| Code Reviewer / 高级工程师 | 代码审查报告、阻塞风险、修复建议 | 工程师 / PI | 代码提交或阶段交付点 |
| 写作者 | 论文草稿、图表、投递材料 | Paper Reviewer A/B / 审稿人 | 章节 / 全文提交 |
| Paper Reviewer A/B | 论文审稿意见、证据/可复现性问题清单 | 写作者 / PI | 论文草稿提交 |
| 审稿人 | 阶段审稿报告、统计合规结论、放行建议 | PI + 写作者 + 科学家 | 阶段交付点 |
| PI | Go/No-Go 决议、投递指令 | 全体 | 审稿/审查后裁决 |

## 4. 阶段交接与放行判据

| 阶段 | 主导 | 配合 | 交付产物 | 放行判据 |
|------|------|------|---------|---------|
| P0 基座 | 工程师 | 数据工程师、Code Reviewer、高级工程师、科学家、审稿人 | Identity/cache 持久化、双文档 Query 格式、基础数据/环境检查 | E0 实现门通过；形状/位置/数值一致性全部通过；关键实现无阻塞审查意见 |
| P1 基准 | 科学家 | 数据工程师、工程师、审稿人 | 六类反事实对、数据 manifest、ridge/consumer/KD 强基线 | 数据切分无泄漏；确认存在未被强基线消除的反事实失真；否则按决策树转向 |
| P2 机制 | 科学家 | 工程师、Code Reviewer、高级工程师、审稿人 | K/V 四臂、层/头移植、局部分解、机制报告 | 机制诊断在验证集有预测价值；实现契约与 zero-re-prefill 无违规 |
| P3 方法 | 工程师 | 科学家、数据工程师、写作者、Code Reviewer | KD-only / CF-lite / CF-mech 训练与消融 | 相对强基线有非偶然改进；数据/代码/指标口径一致；否则停止扩大模型 |
| P4 泛化 | 工程师 | 数据工程师、科学家、审稿人 | 非等深 pair、未见模板/真实文档、封存测试 | 报告跨设置稳定性、CI、失败边界与不利结果；数据来源与 split 可追溯 |
| P5 成稿 | 写作者 | Paper Reviewer A/B、科学家、PI、审稿人 | 投稿 PDF、图表、cover letter | 通过 `docs/protocol.md §10` 贡献表述门槛；论文审查无阻塞问题；PI 签off投递 |

## 5. 硬约束（全角色共同遵守）

1. **判据先写后跑**：`configs/prereg/` 中的 decision rule、`τ`、Huber 阈值必须先冻结；封存测试只读，不得按结果调超参。
2. **Mock 数字不是科学证据**：`--backend mock` 仅用于接线回归与报告格式验证；正式结论只能来自 `--backend gpu`。
3. **严格 zero re-prefill**：Joint 臂禁止学生处理文档 token；每次运行记录 `zero_re_prefill` 标志。
4. **联合报告**：`E_CF` 必须与双向成功率、方向一致率、coverage、无信息控制组差距一同报告，不可单独下降即声称改善。
5. **不可逆产物**：`reports/runs/<run_id>/` 为不可变运行产物；统计结论只能由 `scores.jsonl` 重算。
6. **贡献表述门槛**：仅评价层成立时，改写为边界/实证研究论文，不得保留未被证实的机制/方法措辞（见 `docs/protocol.md §10`）。
7. **数据可追溯与无泄漏**：所有外部数据必须记录来源、许可证/使用条款、下载方式、版本/日期、哈希与处理脚本；训练/验证/测试/封存切分不得泄漏。

## 6. 运行规则（针对 LLM 智能体的专项约束）

1. **审稿人阶段性介入**：审稿人仅在阶段产物提交后介入，不参与日常开发，避免成为沟通瓶颈；每个阶段写改审循环**最多 2 轮**，第 3 轮由 PI 直接裁决。
2. **统计合规性显式化**：审稿人每次介入必须运行 `scripts.bootstrap_ci_report` 与 `scripts.consistency_check`，并核对 `configs/prereg/` 未被动态篡改。
3. **独立审查分离**：Paper Reviewer A/B 只审论文与证据表达，不改代码/数据/判据；Code Reviewer 与高级工程师只审实现与一致性，不改 frozen 判据、不将 mock 结果当科学证据。
4. **否定约束（Hard No's）**：每个角色 Prompt 均列明“绝对不做什么”，负向约束优先于正向指令执行。
5. **文件边界**：每个 Prompt 列明可读/可写/禁止写入路径，防止工程师误改 `configs/prereg/`、写作者误改代码、数据工程师误改运行产物。
6. **数据先行但受控**：数据工程师可在 P1 前准备数据与 manifest，但任何影响评测口径的变更必须经科学家提出、PI 批准并记录版本。
7. **冲突升级**：角色间分歧由 PI 最终裁决，记录裁决理由；不得私自改动冻结判据或测试集指标。

## 7. Prompt 使用说明

`prompts/` 目录包含核心与扩展角色的 System Prompt 模板，可直接注入智能体框架：

| 文件 | 角色 |
|------|------|
| `prompts/pi.md` | PI / 组长 |
| `prompts/scientist.md` | 科学家 |
| `prompts/engineer.md` | 工程师 |
| `prompts/writer.md` | 写作者 |
| `prompts/reviewer.md` | 审稿人（阶段/统计合规） |
| `prompts/paper-reviewer-a.md` | Paper Reviewer A（叙事与证据强度） |
| `prompts/paper-reviewer-b.md` | Paper Reviewer B（方法与实验可信度） |
| `prompts/code-reviewer.md` | Code Reviewer（实现一致性） |
| `prompts/senior-engineer.md` | 高级工程师 / Implementation Auditor |
| `prompts/data-engineer.md` | 数据工程师（数据下载/构造/管理） |
| `prompts/research-advisor.md` | 研究问题顾问（联网评估方向/方案/实验/结果） |

每个 Prompt 包含统一结构：使命 → 在 readkv 中的职责 → 文件边界 → 否定约束 → 交互协议 → 项目硬约束 → 冲突升级。使用时将对应文件内容作为智能体的 system message 即可。

## 8. 未决事项

1. **GPU 后端适配**（唯一剩余技术阻塞）：工程师需实现 `models/hooks.py`，使 `--backend gpu` 可用；详见 `docs/gpu_handoff.md`。
2. **多智能体框架选型**：本协议定义角色与协作协议，不绑定具体框架；可选用 OpenCode subagent、AutoGen、CrewAI 等实现。
3. **阶段排期**：P0–P5 窗口见 `docs/architecture.md §7`，为估算而非承诺；实际时间取决于 GPU 资源与强基线实现可用性。
