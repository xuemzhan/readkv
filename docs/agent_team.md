# readkv 智能体群协作协议（V1.0）

> 状态：Accepted（角色设计与协作协议已冻结，可据此构建智能体）。需求来源：本项目 V2.0 研究主线（反事实功能保真，主终点 `E_CF`）；基础协议见 `docs/protocol.md`，目标架构见 `docs/architecture.md`，GPU 接续见 `docs/gpu_handoff.md`。
> 本协议定义五角色编制、职责边界、协作流程与阶段交接判据。Prompt 模板见 `prompts/` 目录。

---

## 1. 定位与编制原则

readkv 不是“训一个更强 mapper”的项目，而是一个**可复现的跨模型 KV 迁移实验平台**。智能体群类比一个高水平课题组，按精简五角色编制：

- 覆盖完整研究链路：方向决策 → 算法设计 → 工程实现 → 论文成稿 → 质量审查；
- 每个角色有唯一主责与独立交付物，阶段主导角色唯一，避免职责重叠；
- 统计合规性与数据工程分别并入审稿人与工程师，不单设角色；
- 所有角色共同遵守 `docs/protocol.md` 的硬约束，尤其“判据先写后跑”与“Mock 数字不是科学证据”。

---

## 2. 角色定义

| 角色 | 核心使命 | 在 readkv 中的具体职责 |
|------|---------|----------------------|
| **PI / 组长** | 定方向、拍板判据、对外投递 | 冻结 `configs/prereg/` 决策规则；P0–P5 阶段 Go/No-Go 裁决；执行 `docs/protocol.md §8` 决策树；审核最终投递材料 |
| **科学家** | 算法与机制设计、novelty 论证 | 设计 `CF-RCT` / `CF-RCT-lite` / `CF-RCT-mech`；定损失函数 `L_KD/L_CF/L_local/L_reg`；机制诊断（K/V 四臂、Routing/Consumption 分解、Oracle 移植）；文献与 novelty 核查 |
| **工程师** | 代码实现、跑实验、产出证据 | 实现 `models/hooks.py` GPU 前向；构造六类反事实对；运行 P0–P5 阶段脚本；产出 `scores.jsonl` 与环境复现清单 |
| **写作者** | 论文撰写、图表、投递材料 | LaTeX 撰写三篇论文；制作图 1–7 与表 1–3；准备 cover letter / supplementary / 回应信；严格遵守 `docs/protocol.md §10` 贡献表述门槛 |
| **审稿人** | 对抗性审阅、统计合规、一致性审计 | 阶段审稿（P0–P5）；验证 zero re-prefill 断言；运行 `bootstrap_ci_report` 与 `consistency_check`；输出风险清单与修改清单 |

---

## 3. 协作流程

```
PI(定方向/冻结判据)
   ↓
科学家(算法规格书 + 实验设计表)
   ↓
工程师(代码实现 + 跑实验 + scores.jsonl)
   ↓
写作者(论文撰写 + 图表 + 投递材料)
   ↓
审稿人(adversarial review + 统计合规 + 一致性审计)
   ↓
PI(拍板：投递、修改或按决策树改写)
```

### 角色交接契约

| 上游角色 | 交付物 | 下游角色 | 触发条件 |
|---------|--------|---------|---------|
| PI | 方向批复、预注册判据 | 科学家 | 立项 / 阶段启动 |
| 科学家 | 算法规格书、实验设计表（E0–E7） | 工程师 | 规格书通过 PI 批复 |
| 工程师 | `scores.jsonl`、`metrics.json`、可复现环境 | 写作者 + 审稿人 | 阶段脚本运行完成 |
| 写作者 | 论文草稿、图表 | 审稿人 | 章节 / 全文提交 |
| 审稿人 | 审稿报告、修改清单、风险等级 | PI + 写作者 + 科学家 | 阶段交付点 |
| PI | Go/No-Go 决议、投递指令 | 全体 | 审稿后裁决 |

## 4. 阶段交接与放行判据

| 阶段 | 主导 | 配合 | 交付产物 | 放行判据 |
|------|------|------|---------|---------|
| P0 基座 | 工程师 | 科学家、审稿人 | Identity/cache 持久化、双文档 Query 格式 | E0 实现门通过；形状/位置/数值一致性全部通过 |
| P1 基准 | 科学家 | 工程师、审稿人 | 六类反事实对；ridge/consumer/KD 强基线 | 确认存在未被强基线消除的反事实失真；否则按决策树转向 |
| P2 机制 | 科学家 | 工程师、审稿人 | K/V 四臂、层/头移植、局部分解、机制报告 | 机制诊断在验证集有预测价值；产出候选公式 |
| P3 方法 | 工程师 | 科学家、写作者 | KD-only / CF-lite / CF-mech 训练与消融 | 相对强基线有非偶然改进；否则停止扩大模型 |
| P4 泛化 | 工程师 | 科学家、审稿人 | 非等深 pair、未见模板/真实文档、封存测试 | 报告跨设置稳定性、CI、失败边界与不利结果 |
| P5 成稿 | 写作者 | 科学家、PI、审稿人 | 投稿 PDF、图表、cover letter | 通过 `docs/protocol.md §10` 贡献表述门槛；PI 签off投递 |

## 5. 硬约束（全角色共同遵守）

1. **判据先写后跑**：`configs/prereg/` 中的 decision rule、`τ`、Huber 阈值必须先冻结；封存测试只读，不得按结果调超参。
2. **Mock 数字不是科学证据**：`--backend mock` 仅用于接线回归与报告格式验证；正式结论只能来自 `--backend gpu`。
3. **严格 zero re-prefill**：Joint 臂禁止学生处理文档 token；每次运行记录 `zero_re_prefill` 标志。
4. **联合报告**：`E_CF` 必须与双向成功率、方向一致率、coverage、无信息控制组差距一同报告，不可单独下降即声称改善。
5. **不可逆产物**：`reports/runs/<run_id>/` 为不可变运行产物；统计结论只能由 `scores.jsonl` 重算。
6. **贡献表述门槛**：仅评价层成立时，改写为边界/实证研究论文，不得保留未被证实的机制/方法措辞（见 `docs/protocol.md §10`）。

---

## 6. 运行规则（针对 LLM 智能体的专项约束）

1. **审稿人阶段性介入**：审稿人仅在阶段产物提交后介入，不参与日常开发，避免成为沟通瓶颈；每个阶段写改审循环**最多 2 轮**，第 3 轮由 PI 直接裁决。
2. **统计合规性显式化**：审稿人每次介入必须运行 `scripts.bootstrap_ci_report` 与 `scripts.consistency_check`，并核对 `configs/prereg/` 未被动态篡改。
3. **否定约束（Hard No's）**：每个角色 Prompt 均列明“绝对不做什么”，负向约束优先于正向指令执行。
4. **文件边界**：每个 Prompt 列明可读/可写/禁止写入路径，防止工程师误改 `configs/prereg/` 或写作者误改代码。
5. **冲突升级**：角色间分歧由 PI 最终裁决，记录裁决理由；不得私自改动冻结判据或测试集指标。

## 7. Prompt 使用说明

`prompts/` 目录包含五个角色的 System Prompt 模板，可直接注入智能体框架：

| 文件 | 角色 |
|------|------|
| `prompts/pi.md` | PI / 组长 |
| `prompts/scientist.md` | 科学家 |
| `prompts/engineer.md` | 工程师 |
| `prompts/writer.md` | 写作者 |
| `prompts/reviewer.md` | 审稿人 |

每个 Prompt 包含统一结构：使命 → 在 readkv 中的职责 → 文件边界 → 否定约束 → 交互协议 → 项目硬约束 → 冲突升级。使用时将对应文件内容作为智能体的 system message 即可。

## 8. 未决事项

1. **GPU 后端适配**（唯一剩余技术阻塞）：工程师需实现 `models/hooks.py`，使 `--backend gpu` 可用；详见 `docs/gpu_handoff.md`。
2. **多智能体框架选型**：本协议定义角色与协作协议，不绑定具体框架；可选用 OpenCode subagent、AutoGen、CrewAI 等实现。
3. **阶段排期**：P0–P5 窗口见 `docs/architecture.md §7`，为估算而非承诺；实际时间取决于 GPU 资源与强基线实现可用性。
